
# AI Coder reference

This is the detailed reference for the plugin's settings and MCP/IDE tools. Backend availability determines which tools are offered — some are registered only for certain AI types. A session's permission settings do not change the list: a tool the session lacks permission for is still offered and is refused when called.

For what the plugin is and how to install it, see the [README](README.md). For using the NetBeans interface, see the [UI guide](UI_GUIDE.md).

## Settings

Open global defaults at **Tools > Options > AI Coder**. A session may override each applicable option; an unset override inherits the global value.

### General and session settings

| Area | Settings and behaviour |
|---|---|
| Conversation | Maximum history, save history, chat font size, and diff-context lines. |
| Session instructions | Optional session instructions, delivered on the first request or automatically at session startup. |
| Project scope | Restrict file access to the session's selected/open project directories. Enabled by default. |
| Change review | Auto-accept policy and diff presentation. Content changes normally require the NetBeans Accept/Reject review. |
| Inter-AI | Enable messaging, automatic inbox notices, important-message interruption, and the idle AI watcher timer (`CreateIdleWatcher`/`CancelIdleWatcher`/`ListIdleWatchers`). Messaging and automatic notices are off by default; the idle watcher timer is on by default (a session can still turn it off). |
| Web requests | A master switch and separate permissions for HTTP methods, headers, and bodies. GET is allowed by default when web access is enabled; state-changing methods, custom headers, and bodies are off by default. Loopback and private-network destinations are additionally blocked unless their own per-plugin or per-session options — "Allow localhost destinations" and "Allow private network destinations" — are enabled; both are off by default, and a refusal names the exact setting that would permit it. |
| Database | Master switch, read-only sub-permissions, and result-row limit. Disabled by default; the default limit is 25 rows. Only a single SELECT statement is permitted, and the JDBC connection is additionally set read-only for the duration of the query. |
| Git access | Master switch and separate Read/Write sub-permissions. Enabled with both on by default; the built-in ReviewerPeer template sets Write off. See [Git tools](#git-tools) for which of the 21 tools require Read vs Write. |
| Clipboard | Allow reading clipboard text. Disabled by default. |
| Infrastructure | MCP loopback port, save-session-on-close prompting, inbox retention and maximum size, debug JSON/context logging, and tool-use logging. Inbox defaults: 60 minutes and 1,000 messages. |

## Tool use rules

Call `GetInstructions` before other plugin tools. Use the IDE-aware tools below rather than shell equivalents. Paths must be absolute. Tool calls are authenticated for their own session and are restricted by the current permission settings.

- No tool falls back to the file the user is looking at. Pass `filePath` explicitly, and call `GetCurrentFile` when you want the focused editor's file.
- Read a file with `GetFileContent` before changing it.
- Reading or writing a file **saves its unsaved editor changes first**. These tools work on disk, and the editor holds its own copy, so a tool that ignored the buffer would show you text the user cannot see and overwrite the text they can. Flushing first makes the two agree, so what you read is what you edit and the user's work is preserved. The result says so when a flush happened. If the changes cannot be saved the tool refuses outright rather than proceeding and discarding them. Note the Accept/Reject diff is rendered from the file on disk *before* the flush, so it does not display the user's unsaved lines even though the write preserves them.
- For large files, call `GetFileInfo` first and page `GetFileContent` with start/end lines.
- Use semantic refactorings before textual edits whenever possible.
- `WriteFile`, `ApplyEdit`, and content-bearing `SaveFile` show the Accept/Reject diff. `CopyFile`, `MoveFile`, and `DeleteFile` are confirmed as actions, as are shell commands proposed by a backend. **Auto-accept approves the content writes and file actions without asking, but not shell commands, and not a request whose subject the plugin could not identify** — those are prompted every time regardless of the setting. See [Concurrency and limits](#concurrency-and-limits) for how long a prompt waits before it expires.
- Run `GetDiagnostics` before proposing code fixes; refresh file/VCS state after external changes or Git operations.

## Concurrency and limits

These are enforced in code and are not configurable from the UI. They are worth knowing because each one is reachable in normal use.

| Limit | Value | What happens |
|---|---|---|
| Mutating tool calls, plugin-wide | one at a time | Every mutating tool call across **all sessions and backends** is serialised through a single lock — except build, test and download tools, the three IDE build actions, and `SendAiMessage`/`ReadAiMessage`/`DeleteAiMessage`/`MarkAiMessageReplied`/`UpdateSessionDescription`, none of which take it any more (bug fix: a synchronous build or download used to hold this lock for its whole run, so every other session's mutating call — including a plain `SendAiMessage` — waited behind it, up to 310 s). Those tools are serialised by the build queue instead (see below). A call waits up to 15 minutes, then returns a mutation-lock timeout. |
| Resource locks | Git 5 min · Build 5 min (a floor, see below) · Refactor 3 min · File I/O 2 min · Session 1 min · Project structure 5 min | Git, refactoring and file-write tools also take a **global** lock for their resource type — not per project. A concurrent call on an unrelated project is refused immediately with "Resource locked by session …" rather than queued. No build tool takes the Build lock any more — not the Maven/Gradle/Ant build and test tools, not the two Maven download tools, and not the three IDE build actions. The build queue serialises all of them instead (see the next row), so the Build lock's lifetime and wait now serve only as the queue's definition of an inline build's run limit and how long it waits for its turn. |
| Diff and confirm prompts | 120 seconds | An unanswered prompt expires. This is **not** treated as a rejection: the backend is told it may retry, and the panel's buttons stop responding. |
| Build queue (every build tool) | one at a time · one per project · inline waits 120 s to start · then inline 5 minutes or the project's longest successful build + 20%, async 2 hours | All fourteen build tools go through one plugin-wide queue — the nine Maven/Gradle/Ant build, clean-and-build and test tools, the two Maven download tools, and the three IDE actions: first come first served, one build running at a time, at most one build per project queued or running (whoever asks). A request identical to one already queued or running is shared rather than refused: the caller becomes a listener and gets the same result. An inline call waits up to 120 s for its turn to start, then runs to its own adaptive limit — 5 minutes, or this project's longest *successful* build plus 20% when that is longer; an `async: true` call returns its id immediately and may run up to 2 hours once started, delivering the result as a message. The wait and the run limit are separate clocks — time spent queued never counts against the build's own limit. `ListBuilds` shows the queue, `StopAsyncBuild` cancels one of your own async builds — though a *running* IDE action cannot be cancelled, only a queued one. |
| `AskUserQuestion` | 300 seconds | Returns "No response (timed out)". |
| `WebRequest` | 30 s default, 300 s maximum | Set per call via `timeoutSeconds`. |

The plugin-wide mutation lock is the one most likely to surprise: running several sessions concurrently is supported, but their *mutating* work is effectively single-file.

## MCP tools

Every tool additionally takes `sessionId` and `secretKey`, both required — they authenticate the call to the calling session. They are omitted from the Parameters column below, which lists only the arguments specific to each tool.

The MCP server checks both before the tool runs, so a credential failure is a JSON-RPC error (-32600) rather than a tool result. Either one missing gives "Authentication failed: `sessionId` and `secretKey` are both required on every tool call. Copy them verbatim from your session identity block."; a pair matching no session gives "Authentication failed: no session matches that `sessionId`/`secretKey` pair. Re-read your session identity block and copy both values exactly, character for character."

> **Not every constraint appears in the schema.** A tool's declared `required` list does not always describe what it will actually accept. Conditional rules — `GitTag`'s `name` being needed only for create/delete, `ChangeMethodSignature` requiring `name`, `type` and `defaultValue` together for a new parameter, `DeleteAiMessage` needing at least one of `messageId`/`messageIds` — are enforced when the tool runs, not when the arguments are validated. Several tools declare no `required` list at all despite having real constraints. An invalid combination therefore comes back as an error from the call rather than being rejected up front.

### Build tools

**Every** build tool goes through one plugin-wide **build queue** — the nine Maven, Gradle and Ant build, clean-and-build and test tools, the two Maven download tools, and the three IDE actions alike: first come first served across every session, one build running at a time, and at most one build per project queued or running (whoever asks — a *different* build for the same project is refused with "Only one build per project can be queued or running; use ListBuilds to see the queue.", while an *identical* one is shared, see below). Each accepts the optional `async` parameter:

Every Maven, Gradle and Ant build, clean-and-build, test and download tool validates its structured options before queueing: a present option with the wrong JSON type is refused up front, naming the option and the expected type — `properties` must be a key/value map, `goals`/`tasks`/`targets`/`projectList`/`profiles` must be arrays of strings with no non-string entries, `resumeFrom`/`threads`/`testClass` must be strings, and every boolean option must actually be a boolean (`async: "true"` is refused, not treated as true). Omitted or `null` still means "not given," and Maven's `threads` accepts only a positive integer (`4`) or a positive number followed by `C` (`1C`, `1.5C`). The checks follow the build's own system — Maven, Gradle or Ant — not the tool's name.

- **`async: false`** (default) — the call takes its turn in the queue like today: it waits up to **120 seconds** for a free slot, then runs to the inline process limit and returns the full result. That limit adapts per project: **5 minutes**, or the longest non-IDE, non-download build or test tool has taken to finish *successfully* **plus 20%** when that is longer, so a slow project stops being cut off once it has proved how long it needs. Only successful runs count, so a failure or timeout can never inflate it, and successful `async` runs count too — otherwise a project slower than 5 minutes could never succeed inline and its limit could never grow. `ListBuilds` shows the figure per project as `Longest OK run`. If it does not start in time the call returns an error suggesting `async: true`; if it times out while running, the result is prefixed with the same suggestion and the timeout log is attached.
- **`async: true`** — the call returns immediately with the build's **id** and its position in the queue; the build has a **2-hour** time limit once it starts running, and when it finishes the full result is delivered to the calling AI as a message (the chat sees only a one-line summary such as `BUILD: BuildMavenProject SUCCESS in 2 mins, 3 secs (/path/to/project)`, shown as a **system message** alongside tool actions and review logs rather than as though you had typed it). `ListBuilds` shows the queue and recent builds; `StopAsyncBuild` cancels one of your own queued or running async builds. Inline builds cannot be stopped.

Every full result — whether returned inline or delivered as a message — opens with a `Command:` line showing the exact command that ran, arguments containing spaces quoted, e.g. `Command: /opt/netbeans-31/java/maven/bin/mvn clean package -DskipTests -T 2`; the one-line chat summary does not include it.

Asking for a build that is **already queued or running with the same options** — in any key order for a property map, though the same goals, tasks or targets in a *different* order still count as a different build, since the tools run them in that sequence, and profile order is treated as significant too, deliberately conservatively, even though Maven itself activates profiles as a set regardless of order — does not run it twice. The second caller is told the build already exists and who requested it, and is added as a listener: it receives the same result as a message when the build finishes, with the full log copied into its own temp tree so it can actually read it. The build's own requester asking again instead gets a short first-person reply — "You already have this build queued/running as build-N — it was not queued again. Its result will be delivered to you once, when it finishes." — with a `StopAsyncBuild` hint only when that build can actually be stopped right now. Only the AI that requested a build may stop it; when it does, every listener receives the cancelled result too. Closing an AI session removes it as a listener, and a build is cancelled on session close only once nobody is left waiting on it — its requester leaving is not enough while listeners remain, and a running IDE action is left to finish either way.

The three IDE action tools (`BuildProject`, `CleanProject`, `CleanAndBuildProject`) invoke the NetBeans action provider, and they go through the same queue as everything else — they take their turn rather than being refused while it is busy. Where the project reports progress the call waits for the IDE build to finish and returns its result; where it does not (the project's action provider reports nothing, or the request arrived on the UI thread, where waiting would block the very thread the build needs) it returns as soon as the action is triggered and says so, and the result is never reported as a success that could not be confirmed.

Two things differ from the other build tools. A **running** IDE action cannot be stopped: NetBeans gives the caller of `ActionProvider.invokeAction` no cancel handle — the Output window's stop button belongs to the project's own action code — so `StopAsyncBuild` refuses rather than reporting a cancellation that did not happen, and a closing session leaves a running IDE action to finish instead of marking it cancelled. A **queued** one can be stopped normally. Stopping the build yourself in the IDE shows `FAILED` rather than `CANCELLED` because `ActionProgress` reports only a boolean — and since a failed build may show either `FAILED` or `COMPLETED` depending on the project, neither status tells you why a build ended; check the Output window. NetBeans' finished(true) means the IDE action completed, not that the build succeeded: IDE actions show COMPLETED (result unknown) for true, FAILED for false, UNKNOWN (completion not confirmed) when progress is absent, and TIMED_OUT when still running at the limit. Confirm in Output; Maven, Gradle and Ant tools are authoritative.

### Git tools

Git tools are gated by the **Allow git access** master switch and its **Read**/**Write** sub-permissions (both on by default); a call is refused at call time when its permission is off. The five read-only tools — `GetGitStatus`, `GetGitDiff`, `GitLog`, `GitShow`, `GitBlame` — require **Read**; the remaining sixteen require **Write**, including `GitBranch`, `GitTag`, `GitRemote`, `GitStash`, and `GitFetch` even where they only list or fetch without changing the working tree.

Every Git tool requires `projectPath` — target git repository or project root; relative paths resolve against the default project — except `GitBlame`, where it is optional if `file` is absolute. Parameters required only for particular `action`/`operation` values are enforced at call time, not by the schema.
